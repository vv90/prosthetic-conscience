# Consensus LLM Behavior

## Purpose

The consensus LLM is not meant to teach users the internal protocol.

Its job is to:

- hold a natural conversation with the human participant
- infer the participant's likely intent in terms of internal consensus concepts
- verify that interpretation in plain language
- inspect the deliberation state when needed
- prepare local drafts that the human can review and submit

The internal abstractions such as claim, stance, relation, resolve, draft, and grounded semantics are implementation details. The user should usually experience the system as a conversational collaborator that says things like:

- "It sounds like you agree with the hybrid approach."
- "Do you want me to note that down?"
- "Are you saying Alice's condition answers the outage concern?"

rather than exposing protocol jargon directly.

## Current Configuration

The live harness is split across:

- [`llm.rs`](/Users/vladimir/devshells/prosthetic-conscience/crates/prosthetic-conscience/src/consensus_cli/llm.rs), which owns gateway I/O for `pc-consensus`
- [`llm_turn.rs`](/Users/vladimir/devshells/prosthetic-conscience/crates/consensus/src/llm_turn.rs), which owns the pure request construction, response processing, history management, and deterministic follow-up logic

### Tool Loop

- `tool_choice` is now `"auto"`.
- The model can answer directly in plain text when no inspection or draft mutation is needed.
- The LLM-visible tool set excludes `submit_drafts`, `clear_drafts`, and `no_structured_action`.
- Plain-text replies therefore travel through the normal assistant-message path instead of through a fallback tool.

### Hidden Semantics, Natural Replies

- The system prompt explicitly tells the model not to force the participant to understand internal concepts.
- Tool descriptions reinforce that replies should stay in natural language.
- Draft `author` is deterministic engine state from `--participant`, not an LLM-supplied field.

### Clarify-First Drafting Policy

- The current implementation exposes the same LLM-safe tool set on every request.
- Clarify-first behavior is therefore prompt-driven rather than enforced by turn-specific tool gating.
- The prompt explicitly tells the model to ask one short focused question when intent is ambiguous and to avoid drafting until the participant clearly asks or confirms that something should be recorded.

### Deterministic Post-Mutation Follow-Up

After a successful draft mutation, the harness no longer asks the model to narrate what happened.

Instead it deterministically renders a short confirmation from the actual tool result, for example:

- "I've noted that you agree with ..."
- "I've prepared a draft saying that X supports Y."
- "I've prepared a draft for ..."

This avoids:

- runaway extra tool rounds
- spurious links/emojis/garbage text
- misleading statements about submission or commitment
- unnecessary exposure of tool jargon

### Draft-Local References

LLM-visible claim references are flat strings:

- committed claim: `claim:<id>`
- local draft claim: `draft:<id>`

Parsing is consolidated in `ClaimRef::from_json_value` in [`engine.rs`](/Users/vladimir/devshells/prosthetic-conscience/crates/consensus/src/engine.rs). Both tool dispatch in [`tools.rs`](/Users/vladimir/devshells/prosthetic-conscience/crates/consensus/src/tools.rs) and the deterministic mutation confirmation renderer in [`llm_turn.rs`](/Users/vladimir/devshells/prosthetic-conscience/crates/consensus/src/llm_turn.rs) delegate to it. It also accepts the `#<n>` legacy format and `{"claim_id":…}` / `{"draft_id":…}` object forms for backwards compatibility with older tool-call patterns.

## Observed Model Behavior

These observations come from repeated live REPL runs against session `1b810988189c1bc5` on 2026-03-29 while iterating on the harness.

### What Improved

- Summary requests reliably stayed conversational without needing tool calls.
- Exact factual questions often triggered inspection first through `claim_detail` or `preview_claim_detail`.
- Soft preference statements no longer consistently turned into immediate drafts.
- Relation-like remarks improved from being misread as stances to either:
  - an inspected explanation first, or
  - a correct relation draft after explicit confirmation
- Explicit confirmation followed by a recording request now reliably produces the correct draft shape in common cases.
- Post-draft replies are now stable because they are synthesized deterministically instead of generated by the model.

### What Was Previously Fixed by Harness Changes

- Backend/template incompatibility caused by nested claim-ref schemas was fixed by flattening LLM-visible references to `claim:<id>` / `draft:<id>`.
- Plain-text turns now stay plain assistant messages in history rather than being modeled as fallback tool calls.
- Runaway "draft something, then show drafts, then mutate more, then narrate badly" loops were reduced by ending mutation turns with deterministic follow-up text.
- History truncation is safer because `truncate_history()` preserves tool-call/result pairs and only cuts at conversational boundaries.

### Remaining Weaknesses

The remaining issues now look mostly model-limited rather than basic harness bugs:

- Clarification questions can still be generic or overly explanatory.
- On ambiguous fresh turns it may still ask a broad follow-up instead of the sharpest possible disambiguating question.
- Grounding from paraphrased concerns to the exact best graph target is improved but still not consistently excellent.
- Duplicate draft suppression is still incomplete.
- The model is safer now, but not always concise.

In other words:

- action control is much better
- user-facing naturalness is better
- semantic sharpness is still only moderate

## Practical Interpretation

The current setup is now reasonably aligned with the intended product behavior:

- converse naturally first
- verify the participant's meaning
- only then prepare a local draft
- keep submission explicitly human-controlled

For a terminal prototype and tuning harness, this is a good improvement over the earlier direct-drafting behavior.

However, the model still does not behave like a highly skilled conversational facilitator. It behaves more like a decent structured assistant with guardrails.

## Improvement Directions

### 1. Better Model

The biggest remaining lever is a stronger model.

A better model would likely improve:

- sharper clarification questions
- cleaner relation-vs-stance distinctions
- better grounding from paraphrased concerns
- shorter and more natural conversational responses

### 2. Split Conversation and Recording

If one model continues to be mediocre at doing both jobs at once, split them logically:

- conversational clarifier
- structured recorder / validator

That can be done with either:

- two separate models, or
- one model in two separate prompt phases

### 3. Deterministic Semantic Validation

More deterministic validation would still help without becoming a brittle crutch:

- duplicate-draft suppression
- better ambiguity detection before relation creation
- stronger consistency checks between inspected state and drafted targets

This should be based on protocol state and semantic constraints, not word matching.

### 4. Multi-Turn Evaluation

The current eval harness is best for explicit single-turn tool reliability.

To evaluate the actual product goal, add multi-turn conversation evals that measure:

- whether the assistant asked a useful clarification
- whether it avoided premature recording
- whether the follow-up reply after clarification produced the intended structure
- whether the final draft matched the participant's actual intent

### 5. UI Support

The future UI can help reduce model burden:

- show the current local draft as provisional
- let the user approve or tweak wording/strength directly
- make confirmation lightweight
- use audio transcription plus explicit confirmation affordances

That reduces the amount of semantic precision the model must achieve in free-form text alone.

## Current Bottom Line

The harness is no longer the main problem.

It now gives the model a much better behavioral frame:

- hidden protocol concepts
- clarification-first interaction
- deterministic authorship
- deterministic post-mutation confirmation
- a simpler plain-text-or-tool-call loop

The main remaining limitation is the conversational and semantic quality of the current model.
